herdr 0.8.2 plugin · design

Muster

One key opens a screen showing every agent across every repo, ranked by what needs you, styled so you know which is which before you read a word. Enter jumps you there. The same key brings you back.

Name. To muster is to gather a herd, and also to assemble for inspection. Both are what this screen does, and it works as a verb: you muster the agents, then you go back to work.

What I heard, and the two places your answers fight each other

The short version. You want an overlay on one key, not a workspace. It closes when you jump and reopens on the same key. Attention ranking is the single most valuable thing on it. Telling agents apart is a worse pain than seeing them all. The orchestrator writes the context, enforced by a skill the plugin installs. Identity is anchored to the repo, colored by hash with an override. History barely matters because herdr already tracks unseen work. You visit this every 30 seconds.

That last one is a hard constraint, not a preference. A screen you open 100 times a day has to appear in under 30 milliseconds or you stop opening it. It rules out node and python, and it rules out doing any work at open time. Everything must be precomputed.

Contradiction 1: ranking reorders, identity requires it not to

You want the queue ordered by urgency (Q2, Q28) and you want each repo pinned to a fixed spot so you point instead of read (Q23). Those cannot be the same widget. Anything that reorders destroys the spatial memory you're trying to build.

Resolution: two zones. A short ranked ribbon at the top that reorders freely and never holds more than four rows. A fixed repo grid below it where a repo occupies the same cell forever, and urgency shows as a red inset border rather than a position change. Your eye uses the ribbon when you're triaging and the grid when you're orienting.

Contradiction 2: type-to-filter eats every letter key

You picked type-to-filter plus arrows and vim keys (Q16). If bare letters filter, then j and k filter too, and no letter is free for actions.

Resolution: the list is navigable with arrows immediately, and typing any letter enters filter mode where hjkl is literal text. Escape leaves filter mode and gives you vim keys back. Vim keys work only when the filter is empty. Everything else is a modifier chord. It's the mode model fzf and lazygit use and your hands already know it.

The thing your story told me that your answers didn't

Q37 is not a display problem. Four repos in a chain, contracts must merge before api, api usually before web and mobile, sometimes those two go parallel. What broke was propagation. An agent finished, the orchestrator never learned, and three downstream agents sat idle waiting on a gate that had already opened. You went looking for a screen because you had no way to see that the chain had stalled.

So the highest-value thing Muster can show is not agent status. It's a gate that is open with nobody moving through it. Herdr can detect that: an agent went done, the orchestrator has been idle since before that moment, and a downstream agent is idle and has been for longer. That's three facts Muster already has, and the conclusion is "the orchestrator doesn't know yet."

The feature I'd build first

A row in the attention ribbon that reads api/migrations finished 6m ago · orchestrator not told · web + mobile idle, with one key that sends the orchestrator a message telling it. Not a dashboard. A repair button for the exact failure you described.

You also flagged that each workspace has non-agent tabs, dev servers and shells, adding noise. Muster ignores them for triage but shows a one-line footer per repo so you know your dev server is up without opening the workspace. Free information, herdr already has the pane list.

Repo names in every mockup are invented. Muster hardcodes nothing. It discovers repos, colors and sigils them by hash, and works the same on a single repo or fifteen. See discovery, below.

  1. The ranked ribbon. Never more than four rows, reorders freely, disappears entirely when nothing needs you. Row 2 is the propagation repair from your Q37 story.
  2. The chain strip. One line, always the same line, showing where the dependency train actually is. This is the part I'm least sure how to source and I've laid out three options below.
  3. The repo grid. Fixed cells. Api is always position 2 whether it has five agents or none. Empty slots stay visible so nothing shifts when a repo goes quiet.
  4. Attention shows as the red inset border on api, not as a position change.
  5. The footer line is non-agent panes. Your dev servers and shells, present but silent, with a check or cross if Muster can tell whether the process is alive.
  6. The orchestrator strip. Read-only last message, click or prefix+shift+m jumps to its pane, i opens an input that sends through agent prompt.

Spiked and answered: jumping is one call and no race

I expected the overlay's focus restore to fight an outbound focus call. It does not. agent focus the target, then exit. The overlay tears down on process exit and leaves focus exactly where you put it, across workspaces, in about two milliseconds. No close call, no detached helper, no delay.

Measured on 2026-09-05 against 0.8.2: jump from an overlay in w1 to an agent in w2, focus confirmed still correct by an independent process 700ms later, overlay pane gone, no residue in the pane list. No visible flicker.

Where the task line comes from

You chose the orchestrator as the writer, a skill to make it automatic, cwd and branch as the fallback, and the plugin installing hooks for you. Good news from the research: herdr pane report-metadata is a real CLI command, not socket-only. The orchestrator writes context with one shell line and no custom tooling.

# what the orchestrator runs when it dispatches work
herdr pane report-metadata w2:p3 --source muster \
  --title "billing schema migration" \
  --token repo=api \
  --token task="add billing schema migration + backfill" \
  --token blocked_on="contracts#412" \
  --ttl-ms 86400000

Muster ships that as a skill in its plugin root and installs it into your global ~/.claude/skills/ with a single action, plus a CLAUDE.md line telling the orchestrator to call it on every dispatch. Same installer writes the per-repo Stop hook you asked for in Q9, so a worker agent updates its own line when it finishes, and can be re-run to update them all when the format changes.

The dependency chain, which you flagged as the hard one

You want it and you don't know how the plugin would learn it. Three sources, and I'd use all three, in this order.

Inferred from package manifests

Muster reads package.json, go.mod, Cargo.toml, pyproject.toml in each workspace root and matches dependency names against the other repos it knows about. In your chain, web and mobile both depend on the api client package, and api depends on contracts. That draws most of the graph with zero input from you. It runs once per repo on discovery and is cached.

Declared in config, for the edges inference can't see

"This repo must be merged to main before that one can start" is a process rule, not a package dependency. Nothing can infer it. It is a handful of lines you write once and never touch, and if you never write them the chain strip simply does not render. Muster is fully useful with no chain at all.

[chain]
order = [["contracts"], ["api"], ["web", "mobile"]]
# repos in the same bracket can run in parallel
independent = ["infra"]

Runtime edges from the orchestrator

The blocked_on token in the report command above. When the orchestrator parks web on a specific api PR, that's a live edge for this piece of work, not a standing rule. It expires with its TTL. This is what makes the chain strip say PR open ◐ instead of just after api.

Gate state on the strip comes from gh pr view --json state against the branch, cached for a minute. If gh isn't authenticated the strip degrades to the static order with no checkmarks, which is still useful.

A useful accident in herdr's design

The docs say CLI reads do not mark an agent as seen, only focusing does. So Muster can scan every pane continuously and mirror the orchestrator's last message on screen without ever consuming your unseen-work signal. The done state stays honest. That's what makes "unseen since I last looked" enough history for you, and it's why the daemon can be as nosy as it likes.

Notifications go through notification.show, which respects your herdr toast settings and never steals focus. Worth knowing: your [ui.toast] delivery is unset, and the default is off. Muster's installer will offer to turn it on, and won't do it silently.

Architecture

  herdr server
       │  unix socket, event stream
       ▼
  musterd — started once by [[startup]], lives as long as the session
       │   subscribes to pane/agent/workspace/worktree events
       │   scans pane output for errors and the orchestrator's last message
       │   computes attention ranking + chain gates
       │   writes metadata tokens back onto panes
       │   fires notification.show
       │   keeps a snapshot at $HERDR_PLUGIN_STATE_DIR/snapshot.json
       │
       │  reads snapshot, <5ms
       ▼
  muster  — the overlay TUI, spawned fresh on every prefix+m, dies on jump

The daemon is not optional and it isn't about history. It's about the 30 second cadence. If the overlay had to enumerate workspaces, tabs, panes and agents and scan output at open time, you'd wait half a second every time, and you'd stop pressing the key. The client reads one JSON file and draws. Everything expensive already happened.

The daemon is also the only thing that can watch while the overlay is closed, which is the entire notification story and the entire gate-detection story. Without it there is no propagation repair, which is the feature I argued is the most valuable one here.

Failure mode I'll design for up front: if musterd dies, the overlay must still open. It falls back to querying the socket directly, renders in maybe 300ms, shows a small warning in the title bar, and restarts the daemon in the background. A dead daemon degrades the experience, it never blocks you.

Daemon lifecycle: nothing manual, ever

The [[startup]] hook runs once per enabled plugin right after herdr restores your session, before you have looked at anything. So the daemon comes up with herdr and there is no step where you start it. That is the whole point of putting it there rather than in the pane command.

Three details make the difference between that being true and it being true most of the time.

SituationWhat herdr doesWhat Muster has to do about it
You run herdr and the server startsStartup hook fires after session restoreNothing. This is the happy path.
Server already running, you attach a second clientStartup does not re-runNothing, the daemon is already up. But if it died earlier, nothing brings it back, which is why the overlay self-heals.
herdr update --handoffStartup runs again on the new serverMust not spawn a second daemon. A lock file in the state dir, and the second invocation exits quietly.
You link or enable the plugin mid-sessionStartup does not fire. Confirmed, not assumed.The install action starts the daemon itself, so linking Muster works immediately instead of appearing to do nothing.
Headless server, no client attachedStartup still runs server-sideNothing. This is good. Notifications and gate detection keep working while you are away.

Which is why the manifest command is musterd --ensure rather than --daemon. It checks the lock, starts and detaches a daemon if there is not one, and exits immediately either way. Idempotent by construction, so it does not matter how many times herdr calls it.

Why it must detach rather than just run

The docs describe startup hooks as one-shot initialization that should exit when done, and herdr tracks plugin commands with a running or succeeded status and a concurrency limit that returns plugin_command_limit_reached. A startup command that simply never returns would sit in that table as permanently running and eat a slot for the whole session.

So --ensure double-forks and returns in single-digit milliseconds. I have not verified whether herdr also kills or times out a long-running plugin command, and I would rather detach correctly than find out. Same half-day spike.

Combined with the fallback already in the plan, where the overlay queries the socket directly and restarts the daemon in the background if the snapshot is missing or stale, there is no path where you type a command to make Muster work. Worst case it opens slowly once and fixes itself.

Three things the docs do not tell you

All three came out of the spike and all three would have cost an afternoon each if they had turned up later.

FindingConsequence
Manifest commands resolve through PATH, not relative to the plugin root, even though the pane's working directory is the plugin rootbin/muster fails with "no viable candidates found in PATH". It has to be ./bin/muster. Every command in the manifest needs the leading dot.
Closing your own pane with plugin pane close kills the process immediatelyNothing after that line runs. Any cleanup, any focus call, any final write has to happen before it. This is why the jump focuses first.
herdr kills the pane's entire process group on closeA plain forked helper dies with the pane. Anything meant to outlive it needs Setsid. This is exactly how musterd --ensure has to start the daemon, so the spike validated the daemon pattern for free.

Events

The daemon subscribes to the live event stream rather than declaring manifest event hooks, because pane_agent_status_changed and pane_output_changed across seven agents would spawn a process per event and hit plugin_command_limit_reached. Manifest [[events]] is used for exactly two things, workspace_created and worktree_created, which fire rarely and mean "a repo may have appeared, go look at it."

Language

Go, with bubbletea and lipgloss. Reasoning, since you left it to me. Startup has to be single-digit milliseconds, which rules out node and python on your 30 second cadence. Between Go and Rust, this is a styling-heavy TUI with a lot of layout and very little hard computation, and lipgloss is meaningfully better at that than anything in Rust. You said this is an ongoing project, so iteration speed compounds. Both give a single static binary and a trivial [[build]] step for anyone installing from GitHub later. If you'd rather write Rust, ratatui does all of this too and I'll switch without complaint. It's the one call here I hold loosely.

The cost of using the prefix

Prefix bindings are the right default. They compose with herdr's own grammar, they cannot clash with your window manager, and anyone installing Muster gets keys that fit their setup rather than mine. But prefix+m is two keystrokes on something you press every thirty seconds, and that adds up in a way alt+space would not.

So the installer writes the prefix bindings and mentions, once, that you can add a single-chord alias for muster.home if the double tap starts to grate. Your call to make later with real data, not mine to make now.

Two things to verify on a running server

Whether a plugin_action keybinding can open a declared [[panes]] entrypoint directly, or whether it can only invoke an [[actions]] entry that then shells out to herdr plugin pane open. The second definitely works, so this is about saving one process spawn on the hottest path in the whole plugin.

And whether an overlay pane gets a real TTY with a resize signal, since bubbletea needs both.

Discovery: no repo names, anywhere

You want this usable by anyone with any workflow, so nothing about your setup is allowed into the code. Muster learns everything at runtime and stores what it learns in its own state dir, never in the plugin.

QuestionHow Muster answers it with no config
What repos exist?Every workspace has a cwd. git rev-parse --show-toplevel on it gives a repo root. Distinct roots are distinct repos.
What is a repo called?The origin remote, normalized to owner/name. Falls back to the directory basename when there is no remote.
Two clones of the same repo?Same name, different roots. They get the same hue and sigil, and the card header disambiguates by path. Deliberate: they are the same repo.
Two repos with the same basename in different orgs?The owner/name key separates them, so they hash to different hues.
What color and sigil?Hashed from the owner/name key. Deterministic, so the same repo looks the same on every machine you use.
Where does it sit on the grid?Assigned in discovery order on first sight, then persisted in state. Stable forever after. Pinnable in config if you want to rearrange.
What if a workspace has no git repo?It gets a neutral gray card keyed on its cwd. Scratch workspaces still show their agents.
What about the chain?Inferred from package manifests, declared in optional config, and refined by runtime tokens. All three are optional. With none of them the chain strip is hidden.

The consequence worth stating plainly: on a fresh install with zero configuration, someone gets a working colored, sigiled, attention-ranked grid of their repos on first launch. Config only ever exists to override a decision Muster already made.

Identifying the orchestrator

Name plus token, as you picked. One action does both so you never do it twice.

# muster.mark-orchestrator, run once on the pane hosting it
herdr agent rename $TARGET orchestrator
herdr pane report-metadata $PANE --source muster --token role=orchestrator

Detection order is token first, then name, then nothing. The token is authoritative because it survives a rename and can carry more than a string later, things like which repos this orchestrator is responsible for when you eventually run more than one. The name exists because it makes herdr agent prompt orchestrator "..." work from any script, including the reporting skill, without anyone having to look up a pane ID.

If neither is set, the orchestrator strip is replaced by a single line telling you to press a key to mark one. No silent empty space, and no guessing based on which agent happens to talk the most.

Worktrees: supported by the data model, absent from the UI

You do not use them, and you want the door left open. That is a shape decision, not a feature, so it costs nothing to make now and would cost a rewrite to make later.

  • The identity key is (repo, worktree) from the first commit, not repo. Today the worktree half is almost always the main checkout and never renders.
  • herdr's worktree list already returns repo_root, checkout_path, is_linked_worktree and open_workspace_id, so Muster gets this for free without shelling out to git.
  • The card header already reserves a slot for the branch. When worktrees matter, that slot becomes the worktree label and the card grows one row per worktree. No new layout.
  • worktree_created is already one of the two manifest event hooks, so a new worktree triggers discovery on day one whether or not the UI shows it.

The one thing I would not do up front is give worktrees their own grid cell. Five repos with three worktrees each is fifteen cells, which destroys the fixed-position property that makes the grid worth having. When it comes, worktrees live inside the repo card.
